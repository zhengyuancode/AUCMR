# PURE L5 Agent 评价 v4：错误暂挂、完成队列后统一修复

版本：`AUCMR_L5_PURE_AGENT_4.0.0`。本修订响应用户于 2026-11-02 明确提出的“遇到错误跳过、不停止，跑完后统一修复”。旧 v1、v2、v3 的冻结文件、材料、请求、响应、失败及有效记录原样保留。本文件是执行规则修订，不表示正式评价已经完成；参数、实际继承数量、冻结时间和完成度以机器记录为准。

## 修订原因与时间顺序

v3 已形成 28/29 份最终来源参照。T007 的最终来源裁决未给上游候选 RB015 记录 lineage 或明确处置，在预定恢复后失败；其余来源角色已完成。旧执行器虽然处理完来源队列，仍因全局“29 份全部就绪”门控而没有启动任何正式产物评分。

用户本次明确授权更改批次调度：一个目标的技术错误不得阻止其他已具备相同公平条件的目标执行。v4 在第一次正式产物评分之前冻结此规则。主要 C/K/R 及其原子化、分母、空项、Q、未决、聚合与统计定义仍沿用生成前固定的 L5 指标；不得声称本次调度安排在生成前预注册。

## 固定实验条件

材料和顺序仍为既定 29 个目标、58 份匿名产物、相同共同需求与随机队列。源输入、A/B、生成提示、配置和日志不改写，不换目标，不根据产物质量选择重跑或跳过。给定名称与主要参与者不计识别成绩，人工历史稿是待评产物而不是标准答案。

模型、供应商、Junxi 凭据范围、温度、输出预算和超时沿用既有绑定；实际返回模型逐次保存。不得回退其他账户或打印密钥。Qwen 裁决与 Qwen 首判同家族、DeepSeek 首判与生成模型同源的关系继续披露。来源行目录、逐字位置和格式容错边界沿用 v3，不增加一般模糊语义匹配。

队列、项目内目标等权、项目间等权、项目聚类 bootstrap 10000 次及 seed=20261101 保持不变。多个 Agent、继承记录、断言和请求不是独立项目样本。三个指标分别报告，不新增综合分，不以差异不显著证明相当或不劣。

## 从全批次门控改为逐目标配对门控

每个目标的来源参照必须先完整经过构建、独立首稿、先盲读后裁决、复核与有效性检查，并冻结其内容及来源依赖哈希，然后才允许该目标的任何产物进入评分。两个版本使用完全相同的参照哈希、共同来源与评分规则。

首次就绪的 28 个目标可以先完成参照冻结并进入评分。T007 的两个匿名产物均记 `DEPENDENCY_PENDING`，不调用缺少共同参照的评分、不填零、不造空产物、不让一方先使用临时参照。整个固定队列仍保留 29 个目标、58 份产物；暂挂不是排除材料。

后续只有 T007 的来源参照修复成功并单独冻结后，其两个产物才在同样协议下同时成为可执行项。已经冻结并评分的其他目标参照不得为了分数被修改。全体参照最后完成时另存最终清单；初始与逐目标冻结记录均保留，不原地覆盖已经冻结的参照。

来源构建与恢复角色仍只接收共同需求、各自允许的来源草稿和技术错误，不能接触候选产物、方法映射、评分或排名。不同目标的产物可以先评分，不意味着把已出现的分数提供给尚未完成的来源角色。修复选择仅依据技术状态和依赖是否就绪。

## 初轮尽量完成全部固定队列

1. 来源阶段处理全部 29 个目标，每项异常独立登记，其余目标继续。
2. 冻结所有通过完整检查的目标参照；未就绪目标保留依赖暂挂。
3. 两个独立首判角色分别遍历全部 58 个固定匿名位置。参照存在且哈希合法时执行；否则记录依赖暂挂，继续后续位置。
4. 断言对齐、第三角色裁决及固定稳定性抽查同样处理全部预定位置。缺少上游有效记录时暂挂，不把依赖缺失解释为语义结论，不让整批退出。
5. 初轮所有位置处理后，保存错误与依赖队列，再进入统一修复轮。

接口失败、JSON/schema/引用或行政处置缺口属于技术问题；源或语义本身的明确不确定性按原协议保留为 UNRESOLVED、null、Q 或 NA。真实语义不确定性、低分或不利结果不进入“技术修复”重跑队列，不能通过反复请求得到更满意的标签。

## 固定的两轮延后修复

初轮结束后执行最多两轮登记的延后修复。每轮先修复仍缺参照的目标并冻结新就绪参照，再处理这些目标双方以及其他技术失败位置的相关首判、对齐、裁决、稳定性记录。

初轮每个逻辑角色请求只尝试 1 次，遇技术错误立即暂挂并继续其余队列；两轮延后修复各最多 4 次技术尝试。阶段预算固定为 [1, 4, 4]，v4 每个逻辑角色最多 9 次新尝试。旧版本尝试单独保留，不伪装为从未发生。中断恢复必须依靠保存的阶段/尝试记录遵守剩余预算，不能反复启动重置次数。

恢复携带同一实质任务、角色自身的上一条失败响应、具体机械错误和允许的来源行目录；成功判断不重新请求，不覆盖独立首判。不依据 C/K/R 值、方法标签或预期胜负选取修复目标。行政处置缺失不能自动补成“确认”“排除”或来源未决；仍应由限定来源角色给出真实处置及理由。

修复耗尽后仍失败时，程序继续完成汇总，状态为 `FINISHED_WITH_PENDING_ERRORS`（评价尚未完整完成），公布待修复项、受影响配对和潜在缺失偏差。不得以缺失填零、删除固定位置或无依据宣称全部评价完成。

## 继承 v3 的成功记录

v4 可继承 v3 已通过的来源阶段记录，前提为角色与实质输入哈希一致、供应商/模型/参数绑定一致、原记录和原始调用可追溯，并通过新版本兼容验证。v3 中由 v2 继承的记录必须沿原继承链追溯到实际 API 请求与响应，不能把继承 job 当成一次新的 HTTP 调用。

拟检查的记录为 144 条来源角色记录、28 份最终参照；实际接受数量以新继承清单为准。来源义务、标签、理由和原模型元数据原样保留。输入不一致时不得覆盖冻结继承记录，不能静默拿旧判断适配新任务。

v3 没有正式产物评分，所以 v4 的全部产物首判、对齐、裁决、稳定性评价均为首次正式执行。继承与新调用分别计数，不增加独立样本数。

## 记录与最终报告

必须保留逐次原响应和有效首判；裁决、延后修复和技术错误不能覆写首判历史。计划位置、执行状态、依赖暂挂、错误类别、修复阶段、尝试次数及剩余预算均可查询。

交付 `failure_history.json` 保存各阶段错误历史，`pending_errors.json` 保存最终尚未解决项；即使某项后来修复，历史也不删除。最终完成度区分继承来源、v4 新调用、已解决技术失败、未决语义和未完成技术位置。`COMPLETED` 仅表示固定队列的必需技术记录均完成，不表示评价语义正确或已通过人工验证。

指标汇总仍同时报告独立首判均值和裁决结果；逐例、逐项目、总体及 A−B 区间不择优选择。质量统计仅使用合法可评价的配对并披露缺失，不能把 Agent 一致性当作准确性。结论仅限“在选定 PURE 材料及共同证据范围内，Agent 对 AUCMR 生成稿与既有人工文本用例的质量评价”。

## 验证边界

执行前以正式材料之外的合成样例验证：单项异常不阻断其他项、配对参照门控、依赖暂挂不计零、延后修复顺序和预算、已成功记录不重跑、语义 NA 不按技术错误重跑、原始首判不可覆盖、跨版本继承可追溯、最终未完成状态与错误清单一致。

本文不预填测试通过、实际运行或人工确认状态。正式执行与验证结果以机器日志、冻结清单和报告为准。
