# 最终实现、请求与执行记录

## 实际模型和参数

本节依据主结果采用的 1231 个响应和单列补充输入的 6 个响应对应的实际请求载荷核对，不依据历史代码注释。恢复原冻结输入口径不撤销已经完成的评价器修复。

| 项目 | 实际设置 |
|---|---|
| 服务 | 智谱官方兼容 Chat Completions 接口 |
| Base URL | `https://open.bigmodel.cn/api/paas/v4` |
| 模型请求／返回标识 | `glm-4.6v` |
| 输出上限 | `max_tokens=8192` |
| 思考设置 | `thinking={"type":"disabled"}` |
| 流式输出 | `stream=false` |
| 温度、随机种子 | 实际载荷均未显式指定，不能声称温度0或完全确定性 |
| 请求内容 | system/user 文本；不传 PDF 图片，不使用搜索或原生工具 |
| 本地并发 | 顺序调度，共同账本管理发送名额 |
| 密钥 | 仅通过环境变量注入，交接包不含密钥值 |

`glm-4.6v` 是 API 返回的模型标识，不能据此声称服务端权重版本永久固定。当前生成配置使用 DeepSeek-Flash 与 Qwen3.5-Plus，裁判服务属于不同模型系列；这有助于区分生成与评价职责，但不证明评价无偏或等价于真人专家。

## 两组请求与原文索引

每份可评价输出最多组织两组规则请求：

1. vertical：R1–R3。主要提供前置条件、触发、主流程、后置条件，以目标和主参与者为背景。
2. lateral：R4–R7。提供主流程、目标、主参与者、备选流、异常流。

程序先计算规则适用性和 R4 字面充分条件。只把仍需模型判断的规则列入系统消息，要求逐一独立检查，统一返回所有有依据的违规。若一个分组完全由输入适用性或 R4 充分条件解决，不调用模型，直接保存带依据的分组结果。

每条输入断言保留原槽位、原始数组索引和可用的 `step_number`；不会为方便校验而重排、合并或补齐断言。当前提示构造的完整例子见 [data/prompt_examples.json](data/prompt_examples.json)。**主结果采用记录的精确已发送请求**在 [data/accepted_responses.json](data/accepted_responses.json)；补充输入的六份请求单列于 [data/supplemental/accepted_responses.json](data/supplemental/accepted_responses.json)。

## 输出协议

```json
{"violations":[{"rule_violated":"mainflow_trigger_continuity","offending_slot":"main_flow","offending_claim_index":0,"rationale":"Concrete reason grounded in the provided slot text."}]}
```

无违规时返回 `{"violations":[]}`。每条违规只能包含以上四个输出字段；程序映射得到 `rule_id`，用于统计。当前收取流程允许移除包围整个结果的 Markdown JSON 围栏，不猜补截断 JSON，不接受非法字段或越界索引。

最终采用的记录中有一份进行了可追溯的纯引号转义处理，判断、位置、理由和计数未变；本包的响应记录同时保留 `raw_body`、`accepted_body` 和 `syntax_only_adjustment`。这不是对所有模型输出启用宽松纠错的规则。

## 恢复、记录与异常

请求按输入、消息内容、运行目录与稳定请求 ID 建立缓存。已完成分组恢复时复用记录，失败响应保留，不能把新请求伪装成原请求。配置、实现、输入或记录指纹不一致会阻塞使用。

共用费用账本位于 `outputs/evaluation_campaign/budget.sqlite`。发送前登记，响应后保存实际模型、结束原因、原始 usage 和费用估计。费用策略为 `PROVIDER_MANAGED`：平台侧控制支出，本地记录不构成供应商账单硬封顶。发送前名额冲突采用等待，既有已发送请求不会因此自动重发。批处理技术失败累计10项或连续3项停止，严重异常立即停止。

原冻结输入主结果包含 1292 个完成分组：1231 个有模型响应，61 个依据规则适用性／参与者字面出现即可确定。646 项完成记录每项有两个分组；五项无可评价正文不产生有效规则评分。三份补充输入另有六个模型响应分组；历史合并视图才是 1298 个分组、649 项完成，不能用于主表。

## 版本与验证口径

最终执行控制版本为 `L2_R1_R7_RECEIPTS_V5_ALL_ACTIVE_RULES`。最终清单复用了一部分已接受记录；这些记录的精确版本、请求与来源路径随数据保留。因此不能写成“651项均以同一版提示、同一时间重新评价”。这属于最终数据来源说明，无需在论文中叙述调试过程。

验证涵盖：规则文本保持、空槽不适用、R4全流程约束、原始位置校验、失败不计零、缓存不重发、哈希保护，以及构造场景规则检查。既有 V5 验证结果为通过，记录位于 `outputs/agent_l2_rules/full93-rules-v5-20261029/validation.json`；其中 R4–R7 正例控制成功，五个指定记录通过协议检查。离线测试或有限正例校准不能换算成裁判的准确率、召回率或专家一致性。

本交接另提供完全离线的包内校验脚本，复核所有最终计数及论文表，不需要重跑模型。

## 调用和费用

整个 L2 规则评价历史共有1276条请求记录，其中1275条已收到响应，含校准和未被最终选择的响应；本包保留主结果1231份、补充输入6份选用响应，两者合计1237份，与历史总数不能混算为两笔支出。另1条保留为历史未知费用记录，不据此认定供应商实际执行或未执行。历史已记录估算合计3.234992元，包含补充评价，不能称作主实验单独费用。费用估计使用记录中的输入2元/百万token、输出6元/百万token的估算规则，未经平台账单核销，不代表当前价格公告或实际发票。

三份补充输入的 L2 评价共6次响应、估算0.011708元，已包含在上述累计数内。此前生成阶段重跑的费用不包含在 L2 合计内，不得按0元处理。本轮编写交接没有新增模型调用。
